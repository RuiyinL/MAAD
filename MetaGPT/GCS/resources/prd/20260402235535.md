## Original Requirements

The document defines the operational requirements for Gemini Control System (GCS) software. The goal is to provide a functional tool for guiding the development of controls and data acquisition systems consistent with Gemini System operation. It establishes general criteria and specific functional requirements for software and controls design. Users include Astronomers, Science Observers, Telescope Operators, Support Personnel, Developers, and Administrators. The system operates at Observing, Maintenance, and Test levels with specific access modes (Observing, Monitoring, Operation, Planning, Testing, Administrative). Key requirements include remote operations capability, queue-based observing, safety interlocks, data acquisition in FITS format, modularity, and reliability. The software must support multi-instrument contexts, visitor instruments, and ensure safety against equipment damage or human risk.

## Product Goals

- Ensure absolute safety for personnel and equipment through interlocks and monitoring
- Maximize observing efficiency via automated queue-based scheduling
- Support seamless remote operations and multi-site collaboration

## User Stories

- As an Astronomer, I want to submit a queue-based observing program that executes automatically with minimal interaction
- As a Telescope Operator, I want to monitor all subsystems and intervene quickly if unsafe conditions arise
- As a Support Personnel, I want full access to subsystems for maintenance and diagnostics without affecting ongoing observations
- As an Administrator, I want to view system utilization and scheduling status without controlling hardware
- As a Developer, I want to test subsystems in a virtual telescope environment before deploying to hardware

## Competitive Analysis

- VLT Control System (ACS): Highly modular, strong remote support, complex architecture
- Keck Control System: Robust real-time control, limited remote observing compared to Gemini
- HST Control System: Highly automated, ground-based support strong, no real-time user interaction
- EPICS Framework: Standard for scientific control, lacks high-level observing logic out-of-box
- SOFIA (ESO): Modern architecture, good integration, specific to ESO infrastructure
- ObsCore: Generic observatory control, less specialized for 8m telescope nuances
- Industrial SCADA Systems: High reliability, lacks astronomical specific data handling (FITS)

## Requirement Analysis

The Gemini Control System requires a highly modular, safety-critical architecture. Key constraints include strict operational levels (Observing, Maintenance, Test) and access modes that dictate user privileges. Safety is paramount, requiring hardware interlocks independent of software. Remote operations must be transparent despite bandwidth limitations. Data integrity is critical, requiring FITS format storage and archiving. The system must handle multi-instrument contexts and visitor instruments via stable interfaces. Reliability features like retry procedures, self-tests, and fault notification are essential. The UI must reflect access modes clearly while maintaining a homogeneous look-and-feel across subsystems.

## UI Design draft

The UI must be mode-dependent. Observing Mode: Simple, safe interface for astronomers with queue status and quick-look data. Operation Mode: Detailed control panels for operators with emergency stop visibility. Maintenance/Test Mode: Full diagnostic access for support staff. Common elements include status dashboards, log viewers, and configuration tables. The design should be homogeneous across subsystems but visually distinct based on access level (e.g., color coding for modes). Remote interfaces must mirror local functionality with bandwidth optimization.
