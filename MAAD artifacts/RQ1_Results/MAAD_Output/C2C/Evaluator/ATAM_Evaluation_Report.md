## A. Executive Summary

The Center-to-Center (C2C) architecture enables robust, secure interoperability between heterogeneous Texas DOT Traffic Management Centers by normalizing traffic/device data into a canonical repository using ITS standards (TMDD/DATEX/ASN/TCP/IP), supporting map-centric visualization, incident/lane-closure workflows, and password-authenticated remote device control. Key safety/security mechanisms include strict RBAC, mTLS for control, hash-chained audit, and adapter-based legacy integration. Architecture is aligned to the provided 4+1 diagrams (*UseCase_ScenarioView:UC_ViewMap,UC_IssueDeviceCommand*; *Sequence_ProcessView_S1, S2*; *Deployment_PhysicalView*).

**Top 5 prioritized business goals:**
1. BG-01: Ensure secure, authorized remote device control across diverse traffic centers (P0).
2. BG-02: Federate traffic data and incidents for statewide situational awareness (P0).
3. BG-03: Support interoperable, standards-based integration with new and legacy ITS partners (P1).
4. BG-04: Enable high-availability with robust auditability for regulatory and operational assurance (P0).
5. BG-05: Minimize operational cost by modularizing/incrementally modernizing legacy code (P1).

**Top 5 findings:**
1. F-01 (Risk): Legacy Windows/ESRI platform lock-in presents medium/high upgrade/security risk (INF-072, INF-074).
2. F-02 (Risk): Interoperability drift (TMDD/ASN schema mismatch) is a moderately likely cause of cross-agency data loss (INF-034, INF-035).
3. F-03 (Strength): Security controls (mTLS, password policy, audit chain) are strong for remote commands if mTLS and RBAC are strictly enforced (INF-SEC-002, INF-070).
4. F-04 (Non-risk): Repository/data pipeline is horizontally scalable and meets SLOs under current design due to stateless services and indexed DB (INF-079, INF-PERF-01).
5. F-05 (Recommendation): Immediate priority for safe rollout is adapter conformance test automation and CI/CD for contract validation (INF-034, INF-079).

## C. Concise Architectural Presentation

The C2C architecture is a microkernel-based data exchange platform (see *Package_DevelopmentView*, *Component_DevelopmentView*) connecting peer and legacy TMC systems. The core is a service and repository layer (Windows/SQL) with:
- **Adapters** (plugins) for TMDD/DATEX/ASN interop, with version negotiation and schema validation (*Class_LogicView:TMDDCodec*, *Component_DevelopmentView:AdapterBroker*).
- **Secure APIs and Web UIs**: All public endpoints (APIGateway) are protected by TLS 1.2+; device command endpoints use mTLS and enforce RBAC claims with strict password/MFA policies (*Sequence_ProcessView_S1_IssueDeviceCommand*, *Activity_ProcessView_RemoteDeviceCommand*).
- **Canonical Data Repository**: All traffic/incident/device data are normalized and indexed by (networkId, deviceId, timestamp), with immutable hash-chained audit (AuditEvent).
- **Visualization & Map Integration**: Map overlays, incidents, and device icons are served through ESRI ARC IMS endpoints; overlays are generated by MapService with config-driven speed thresholds (see *MapService*, *Sequence_ProcessView_S2*).

**Key architectural decisions:**
| DecisionID | Decision | Rationale |
|---|---|---|
| D-01 | Microkernel + plugin adapters | Decouples legacy interop, enables per-center customization. [INF-001-036] |
| D-02 | Global canonical SQL repository | Ensures consistent state and enables resilient audit. [INF-079, INF-AUD-001] |
| D-03 | mTLS+RBAC for remote command | Meets strong security needs for control actions. [INF-SEC-002, INF-070] |
| D-04 | Version negotiation + schema validation for TMDD | Prevents silent data loss and adapter drift. [INF-034, INF-035] |
| D-05 | Hash-chained audit logging | Tamper evidence and regulatory support. [INF-AUD-001] |
| D-06 | Kubernetes-ready packaging | Supports future-proofing under modernization. [INF-PLAT-01] |

## F. Architecture Evaluation (Scenario-based Analysis)

### **Walkthroughs for Top Scenarios (≥8)**

#### **Scenario QAS-01 (High): Remote command submission + status**
- **Step-by-step (ref: Sequence_ProcessView_S1_IssueDeviceCommand):**
    1. RemoteControlOperator launches RemoteControlGUI (Deployment_PhysicalView:RemotePC::RemoteControlGUI).
    2. User authenticates with password (≥12 chars), mTLS required by APIGateway (APIGateway/Activity_ProcessView_RemoteDeviceCommand).
    3. AuthService enforces lockout/MFA/RBAC (AuthService).
    4. Operator selects device, enters command.
    5. DeviceCommandService checks CommandTimeframe, validates schema (State_LogicView_DeviceCommandLifecycle).
    6. Command routed via AdapterBroker to correct ExternalTrafficSystemAdapter.
    7. TMDDCodec encodes/negotiates (TMDDCodec.validateSchema).
    8. Command status returned (PENDING/SUCCESS/FAILURE) and displayed in GUI within 2s.
    9. AuditEvent written (Class_LogicView:AuditEvent).
- **Sensitivity:** mTLS support (APIGateway), RBAC claim (DeviceController), TMDD version (adapter).
- **Tradeoffs:** Security (strong mTLS/lockout) can slightly slow performance; SLO is 2s.
- **Confidence:** High (full coverage in diagrams/artifacts).

#### **Scenario QAS-02 (High): Incident ingest from peer**
- **Step-by-step (ref: Class_LogicView:TMDDCodec, Deployment_PhysicalView:Adapters):**
    1. ExternalTrafficSystemAdapter receives TMDD/DATEX/ASN payload.
    2. TMDDCodec validates and parses, logs negotiated version.
    3. On schema mismatch, incident is quarantined and error logged.
    4. Incident is normalized and written to Incident table (sql/incident_ddl.sql).
    5. Notification exposed via IncidentService.
- **Sensitivity:** TMDDCodec schema, AdapterPlugin version handling.
- **Tradeoffs:** Strict schema can drop non-conforming data; leniency creates risk of silent errors.
- **Confidence:** High (adapter/test coverage; see openapi.yaml and internal.proto).

#### **Scenario QAS-05 (High): DB failover during ingest**
- **Step-by-step (ref: Deployment_PhysicalView:DB, AdapterBroker):**
    1. DB fails; Adapters cannot write.
    2. MicrokernelRuntime's ingest queue waits/retries per policy.
    3. On DB restore, adapters resume, outbox flushes.
    4. Audit log gaps detected and verified via hash chain (AuditLog).
    5. SRE alarms on ingest error rate.
- **Sensitivity:** Repo write path, adapter retry, audit recovery.
- **Tradeoffs:** High HA config increases ops cost, reduces downtime risk.
- **Confidence:** Medium-High (HA arch in DB and reviewable failover procedure).

#### **Scenario QAS-07 (High): RBAC regression**
- **Step-by-step (ref: UseCase_ScenarioView:UC_AuthorizeAction, Activity_ProcessView_RemoteDeviceCommand):**
    1. User authenticates, claims issued in JWT/access token.
    2. On each protected endpoint, SecurityGateway enforces RBAC mapping.
    3. Unauthorized claims result in access denied with audit trail.
    4. Incidents of claim misassignment surface as audit log anomaly.
    5. SRE monitors for privilege escalations.
- **Sensitivity:** AuthService mapping, audit, security reviews.
- **Tradeoffs:** Strictness may necessitate more breakglass/emergency flows.
- **Confidence:** High (defense in depth, tracked audit events).

#### **Scenario QAS-08 (High): Password brute-force defense**
- **Step-by-step (ref: Activity_ProcessView_RemoteDeviceCommand, AuthService):**
    1. Attacker attempts multiple logins via RemoteControlGUI.
    2. After 5 failures, account is locked for 30 minutes.
    3. Each attempt logs AuditEvent; no password stored.
    4. SRE alert fires on lockout spikes.
- **Sensitivity:** Login rate limits, lockout config.
- **Tradeoffs:** Aggressive lockout policies prevent brute-force but may increase lockouts for legitimate users.
- **Confidence:** High (artifact and code policies enforce this).

#### **Scenario QAS-06 (High): Audit tamper detection**
- **Step-by-step (ref: Class_LogicView:AuditEvent):**
    1. Operator/attacker deletes/modifies log row in audit_event.
    2. Next audit log read scans chain; hash mismatch is immediately detected.
    3. SREs alerted, incident response per runbook.
    4. Hash chain recomputed on restore/slack.
- **Sensitivity:** AuditLog chain integrity.
- **Tradeoffs:** Crypto hash append overhead (minimal at current volume).
- **Confidence:** High (table and application code enforce this).

#### **Scenario QAS-03 (Med): Map/overlay request at peak**
- **Step-by-step (ref: Sequence_ProcessView_S2_ViewMapAndIncidents):**
    1. WebMapUI sends request to MapService via APIGateway.
    2. MapService fetches latest link speeds/incidents from TrafficRepository.
    3. MapRenderService overlays color codes via thresholds YAML.
    4. Overlay rendered within 1s for p95 under nominal load.
- **Sensitivity:** MapService cache policy, ESRI rendering latency.
- **Tradeoffs:** Lower TTLs can increase DB load; bigger caches increase staleness risk.
- **Confidence:** Medium (benchmarked, but rails on ESRI performance).

#### **Scenario QAS-04 (Med): Adapter plugin hot upgrade**
- **Step-by-step (ref: Package_DevelopmentView:pkg_kernel):**
    1. Ops signals MicrokernelRuntime to reload/restart adapter.
    2. Plugin ABI boundary ensures isolation.
    3. AdapterBroker routes new traffic to replacement plugin.
    4. Old plugin drained; error metrics collected.
    5. Any failures in version negotiation are logged and quarantined.
- **Sensitivity:** Runtime plugin ABI, error reporting, upstream adapter support.
- **Tradeoffs:** Live upgrades risk transient connectivity loss.
- **Confidence:** Medium (actual zero-downtime depends on plugin/test quality).

## L. Assumptions & Open Questions

**Assumptions**
- A1: “Windows NT” means Windows Server 2019+ except where exact WinNT binaries are required.
- A2: ESRI ARC IMS 10.2 and Map Objects are available/supported.
- A3: TMDD v3.0+ ASN.1 schemas are supplied or available for all partners.
- A4: All external centers support TLS 1.2+ (or a secure tunnel is acceptable as fallback).
- A5: Devices beyond DMS/LCS/CCTV are handled via `deviceType`+`device_ext` for now.
- A6: Tabular fields for incidents include: id, description, roadway, timestamp, impact, status.

**Unresolved stakeholder questions**
- What exact TMDD version(s) and ASN.1 modules will partners require?
- Who is the authoritative owner for networkId/devices list per agency (mapping changes/ownership)?
- Are any incident fields considered PII or under stricter data retention/deletion policy?
- How is `CommandTimeframe` configured per network/device—central or per partner?
- What are regulatory mandates for audit log retention and cryptographic signing?

**Diagram naming conflicts**
- Diagram entities refer to “Windows Server 2019+” but SRS states “Windows NT”. Canonical reference is SRS (A1 notes implementation).
- Some diagrams use NFR/ASR IDs not present in SRS; all such requirements are labeled as `INF-xxxx`, explained and listed above.

## M. Validation, Metrics & Confidence

**Validation activities**
- **Load test**: Remote device command throughput ≥100/sec; 99% command response ≤2s (INF-070).
- **Schema conformance**: Partner adapters must pass 100% of TMDD/ASN message validation suite (INF-034/035).
- **Security test**: SAST/DAST run for all components; DAST includes mTLS negative tests and password brute-force attempts (INF-SEC-002/003).
- **Failover test**: Simulate DB and adapter failover; observe zero data/command loss, RTO ≤1hr (INF-AVAIL-01, INF-079).

**Metrics & SLOs**
- p95 command response <2s on all device commands
- No failed mTLS connections on control endpoints (>99.99%)
- 100% audit chain integrity after any restore
- 0 severe privilege escalation events in RBAC audit

**Quantitative modeling**
- Ingest queue modeled as M/D/1 (inputs: adapter event rate, DB write rate), capacity set for no reject at p99
- Anticipated operator login load <10/sec; lockout threshold at 5 tries/user/30min for brute-force resistance

**Confidence**
- High: All key risk scenarios are covered in diagrams, code/contract artifacts, and validation plans, with conservative assumptions. Periodic SRE/Audit reviews mandated.

# scenario_executions.md

### QAS-01: Remote command walkthrough
- RemoteControlOperator authenticates (GUI → APIGateway → AuthService).
- mTLS validated at gateway; RBAC "DeviceController" checked.
- Command entered (GUI → DeviceCommandService).
- Validate schema/timeframe; TMDD encoded; command sent to AdapterBroker → AdapterPlugin.
- Ack/status returned by AdapterPlugin → GUI; status displayed ≤2s.
- AuditEvent written (user, action, commandId, timestamp, hash chain).

### QAS-02: Incident ingest from peer
- AdapterPlugin receives TMDD/DATEX/ASN payload via TCP/IP+TLS.
- TMDDCodec validates, parses, negotiates version.
- Valid incidents inserted into Incident table; invalid quarantined.
- Insert confirmed in repository; new incident available in IncidentService/map overlay.

### QAS-05: DB failover during ingest
- Repo fails; AdapterBroker logs error, retries per config.
- On primary promotion or DR restore, AdapterBroker resumes ingest.
- Audit chain checked for gaps (hash chaining).
- No incidents/commands lost; SREs notified of downtime; SLOs checked.

### QAS-07: RBAC regression
- User logs in; gains incorrect claims due to misconfig.
- SecurityGateway enforces claim at each endpoint; unauthorized op is denied and audited.
- AuditEvent written for all attempt outcomes.
- Semiannual RBAC reviews reveal unexpected assignments.

### QAS-08: Password brute-force attempt
- Attacker triggers >5 login attempts on an account.
- AuthService locks account 30min; AuditEvent records attempts.
- SRE alarm on spike lockouts in metrics.

### QAS-06: Audit trail tampering
- Attempted audit log row delete detected by next log reader via hash-prev/hash-this mismatch.
- Runbook for integrity check/restore invoked.
